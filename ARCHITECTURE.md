# DYOJ (Design Your Own Jewelry) - System Architecture

## 1. Overview

DYOJ is a jewelry e-commerce application allowing users to upload AI-generated or inspirational jewelry designs. These are processed to calculate the price (minimum 200 euros, scaling by size and weight) for 3D printed silver ornaments. The system facilitates order placement, payments, manufacturing tracking, and realtime shipment tracking.

The application is built for extreme scalability, resiliency, and a fluid user experience across all devices (Desktop, Tablet, Mobile) using a microservices backend and a microfrontend UI architecture.

## 2. Technology Stack

### Frontend (Microfrontend Architecture)

* **Framework:** React 18+ with TypeScript.
* **Microfrontend Implementation:** Webpack Module Federation or Vite Module Federation. Enables independent deployment of distinct UI parts (e.g., Core/Shell, Catalog/Upload, Checkout, User Dashboard).
* **State Management:** Zustand (for local/shared microfrontend state) and React Query (for server state, caching, and background syncing).
* **Styling:** Tailwind CSS for fluid, responsive UI across devices.
* **Realtime Communication:** WebSockets / Server-Sent Events (SSE) for pushing Kafka event updates to the UI (e.g., tracking updates).

### Backend (Microservices Architecture)

* **Framework:** Java 17+ and Spring Boot 3.x.
* **API Gateway:** Spring Cloud Gateway (handles rate limiting, routing, SSL termination, and token validation).
* **Inter-Service Communication:** REST (Synchronous) and Apache Kafka (Asynchronous/Event-Driven).
* **Service Discovery:** Kubernetes CoreDNS (abstracts Eureka away for cloud-native deployments).

### Data & Infrastructure

* **Database:** PostgreSQL (Primary relational store for transactional data).
* **Caching & Rate Limiting:** Redis.
* **Message Broker:** Apache Kafka.
* **Payment Gateway:** Stripe (Recommended for security, ease of use, idempotency support, and extensive global webhooks). Alternative: Adyen (often better pricing at enterprise scale).
* **Containerization & Orchestration:** Docker & Kubernetes (Helm charts for deployment).

## 3. Microservices Split

Instead of a monolithic repo, the system is split into the following repositories (represented as directories here):

1. **`dyoj-ui`**: The React-based frontend application (can be further split into `dyoj-ui-shell`, `dyoj-ui-checkout`, etc.).
2. **`dyoj-api-gateway`**: Entry point for all clients. Handles cross-cutting concerns (Auth, Rate Limiting, CORS).
3. **`dyoj-user-service`**: Manages User profiles, Vendor data, Authentication (JWT), and Authorization.
4. **`dyoj-catalog-service`**: Manages uploaded designs, 3D printing feasibility validations, sizing, weight estimations, and pricing logic.
5. **`dyoj-order-service`**: Manages cart, checkout, and order state machine. Handles **idempotent requests** to prevent duplicate orders.
6. **`dyoj-payment-service`**: Integrates with Stripe. Processes webhooks and updates payment statuses securely.
7. **`dyoj-tracking-service`**: Integrates with cargo/shipment APIs (e.g., BlueDart, FedEx). Polls or receives webhooks for real-time status. Falls back to manual AWB tracking if API is unavailable.
8. **`dyoj-notification-service`**: Listens to Kafka events and pushes WebSocket events/emails to users.

## 4. High-Level Architecture Flow

1. **Upload & Quote:** User uploads an image -> `dyoj-api-gateway` -> `dyoj-catalog-service`. Service analyzes image/metadata, estimates weight/size, calculates price (>200 EUR).
2. **Order Placement (Idempotent):** User checks out. `dyoj-order-service` creates an order in `PENDING` state. An idempotency key (e.g., a UUID generated by the UI) is used to ensure network retries don't create duplicate orders.
3. **Payment:** `dyoj-payment-service` calls Stripe to create a PaymentIntent. UI completes payment. Stripe webhook notifies `dyoj-payment-service`, which emits a `PaymentSuccessEvent` to Kafka.
4. **Order Fulfillment:** `dyoj-order-service` consumes `PaymentSuccessEvent` and updates order status. `dyoj-catalog-service` is notified to prepare manufacturing.
5. **Shipment Tracking:** Once manufactured, tracking info is created in `dyoj-tracking-service`. This service polls the cargo provider. On status change, it emits a `TrackingUpdatedEvent` to Kafka.
6. **Realtime UI Update:** `dyoj-notification-service` consumes `TrackingUpdatedEvent` and pushes the update to the UI via WebSockets. If the WebSocket connection is missed, the UI's `React Query` fetches the latest state upon focus/reconnect.

## 5. Resiliency & Best Practices

* **Idempotency:** All state-mutating POST/PUT endpoints use an `Idempotency-Key` header. `Redis` stores the key for 24h to return the cached response.
* **Circuit Breakers & Retries:** Implement Resilience4j on all inter-service REST calls (e.g., between Order and Payment services). Configure Exponential Backoff and Jitter to prevent thundering herds.
* **Database-per-Service Pattern:**
    To ensure loose coupling and independent scalability, each microservice owns its data. They use separate databases (or isolated schemas/roles) within the PostgreSQL cluster.
  * **User Service DB (`dyoj_user_db`):** `users` (id, email, password, role), `profiles` (name, addresses).
  * **Catalog Service DB (`dyoj_catalog_db`):** `designs` (id, user_id, image_url, weight, dimensions, calculated_price).
  * **Order Service DB (`dyoj_order_db`):** `orders` (id, user_id, status, total, idempotency_key), `order_items`.
  * **Tracking Service DB (`dyoj_tracking_db`):** `shipments` (id, order_id, provider, awb_number, status_history).
* **Observability:**
  * Micrometer with Prometheus endpoints in all Spring Boot apps.
  * Grafana dashboards for p50, p95, p99 latencies, CPU/Memory (Kubernetes Pods).
  * Distributed Tracing (Sleuth/Micrometer Tracing + Zipkin) passing `traceId` across all microservices.

## 6. Realtime & Fallback Mechanism (UI)

* **Event Bus (Kafka) -> Notification Service -> WebSocket -> UI**
* **Fallback:** To handle missed Pub/Sub events (e.g., network drop on mobile), the UI uses a polling fallback or visibility-change hooks to issue a standard GET request to `dyoj-order-service` to reconcile the current state.

## 7. Next Steps for Implementation

1. **Initialize Git Repositories**: Create separate repositories as outlined in section 3.
2. **Setup Infrastructure**: Use the provided `docker-compose.yml` to spin up PostgreSQL, Redis, and Kafka locally.
3. **Bootstrap Backend**: Use Spring Initializr to bootstrap the services. Implement the `dyoj-api-gateway` and `dyoj-user-service` first.
4. **Bootstrap Frontend**: Initialize the React app using Vite (with Module Federation plugin if splitting further). Setup Tailwind and Zustand.
5. **Implement Core Flow**: Build the image upload, pricing, and idempotent order creation flow.
6. **Integrate Payment**: Add Stripe API and webhooks.
7. **Realtime Notifications**: Implement the WebSocket/SSE layer with Kafka consumers.
